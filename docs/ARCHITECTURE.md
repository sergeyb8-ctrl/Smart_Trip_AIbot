# Архитектура SmartTrip

## Единый поток

Telegram aiogram → анкета кнопками ИЛИ AIParser → Draft → уточнение пропусков → TripRequest → каталог SQLite → Trip Engine → сохранение результата → Telegram.

Draft: извлечённые параметры, допускающие null.
TripRequest: только Санкт-Петербург, 1–5 дней, целый рублёвый бюджет, хотя бы один интерес, исключения, темп, время.
Ни один результат LLM не считается готовым маршрутом.
Перед построением пользователь подтверждает полный набор параметров.

## Компоненты

- telegram.py: UI, FSM, проверки владельца истории и администратора.
- ai.py: строгий JSON от Groq, резервный Gemini, локальная валидация.
- engine.py: независимый Python-модуль без сетевых вызовов и токенов.
- database.py: SQLite places, trips, sessions.
- settings.py: чтение секретов из .env; в repr они не включаются.

Анкета хранится в SQLiteStorage; события одного пользователя последовательно выполняются через SimpleEventIsolation.
Callback-кнопки имеют идентификатор текущей анкеты. Старые кнопки после отмены или новой анкеты не меняют актуальные параметры.
Чтение истории требует одновременно user_id и id поездки; угаданный чужой id не даёт доступ.

## Алгоритм рекомендаций и маршрута

1. Исключить объекты с любым запрещённым тегом.
2. Оставить объекты хотя бы с одним интересующим тегом.
3. Оценка: 10 × число совпавших интересов + 2 для объекта с нулевой оценкой стоимости.
4. Зарезервировать по 800 ₽ на каждый день.
5. Разделить оставшийся бюджет посещений между оставшимися днями.
6. Первую точку выбрать с учётом плотности соседних подходящих объектов.
7. Далее выбирать максимальную оценку полезности с поправкой на расстояние от предыдущей точки.
8. Проверять расход, лимит ходьбы, длительность, переходы и конец дня до 20:00.
9. Не повторять объекты между днями.
10. Если на каждый день не хватает подходящих объектов — объяснить невозможность.

Темп задаёт 3/4/5 точек и 5/8/12 км между ними. Скорость ходьбы 3,5/4/4,5 км/ч.
Переходы оцениваются по haversine × 1,3. Один 45-минутный перерыв может добавляться около 13:00.
Это эвристика, а не доказательство глобально кратчайшего маршрута.

## Границы первой версии

Без календарных дат не проверяются выходные и сезонные часы работы. Строки OSM справочные.
Время рекомендательное. Точные уличные маршруты и реальное наличие билетов не определяются.
Каталог не обновляется автоматически; обновление исходного JSON выполняется отдельно.
Расчётные цены не равны актуальным тарифам.
Нет обученной рекомендательной ML-модели. Работает описанный собственный алгоритм.
Нет бронирования, оплаты, межгородних и зарубежных поездок.
Эти ограничения должны оставаться в отчёте до реализации и проверки соответствующих функций.
